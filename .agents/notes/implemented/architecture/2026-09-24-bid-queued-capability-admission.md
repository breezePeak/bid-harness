# Agent Note: Bid 能力请求的持久队列接纳

Status: implemented

## Problem

公开主会话在长时间运行的阶段工作中仍会收到跨阶段修改请求。直接启动第二个 Run 会让两个写入者争用同一项目；只保留内存请求会在重启后丢失授权。

## Decision

`bid_run_task` 在已有 Run 持有项目时先写入不可变请求，再把 `enqueue_capability_task` 引用登记到该 Work 的 `commands.json`。只有日志中的 pending 命令构成接纳。原 Run 结束后按日志顺序取得独立执行槽；applied 表示新 Work 已持久化接纳，不表示能力成果完成。

恢复扫描仅查看持久命令日志。若同一用户消息的能力 Work 已启动，调度器等待其恢复或完成；完成后通过项目 mutation 标记原命令，避免再次创建 Run。S5 热插入控制器只消费写作命令，并在提交前重新读取共享日志。重置删除必要输入时将保留下来的排队命令标记为 canceled。

## Alternatives considered

内存数组无法跨重启恢复。把排队任务立即交给新 Run 会突破单写者约束。扫描所有请求文件会把尚未登记的孤立请求误认为用户已接纳的任务。

## Consequences

请求接纳与实际执行之间有明确的 Work 边界，并保留可验证的命令身份。队列只在原工作收敛后调度，局部任务不会抢占正在运行的默认阶段；挂起的原工作保留恢复控制权。
