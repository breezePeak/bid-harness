# Agent Note: Bid 同一 Work 的能力步骤与结果发布

Status: implemented

## Problem

跨阶段修改需要多个能力协作。按阶段分别启动 Run 会让前一步的目标身份、已完成文件和用户授权散落在不同恢复记录中；直接发布整个章节目录又可能覆盖任务范围外的正式成果。

## Decision

`capability_task` 是单一 Work kind。不可变请求绑定真实用户消息、任务目标、根范围、初始步骤、正式输入摘要和任务前状态；Host 生成 Work 与步骤 ID。`BidRunCoordinator` 为整个序列只接纳一个有效根 Run，步骤共用该 Run 的取消、Child 收敛与提交权限。`runs/<workId>/task-checkpoint.json` 记录完成结果、运行中步骤、等待输入和由后续真实用户消息授权的计划补丁；补丁只能替换尚未开始的后缀，不改请求 SHA。

每一步使用独立候选目录。Host 按当前确认目录、任务根范围及前一步的真实 `target_section_ids` 解析作用域；适配器只能声明预先允许的精确文件。业务 Validator 核对结果后，步骤文件和步骤回执同批合并到 Work 候选。最终发布只替换已核对的文件，并在同一 PublicationBatch 写入 `requests/<workId>/result.json`。该凭据保存请求 SHA 与文件摘要，不复制正文。

重启首先前滚已有发布事务，再校验正式凭据及文件。正式提交已完成时，Host 只补任务前状态、Run 完成事件和公开主会话的有界结果通知；没有提交凭据时从检查点与候选回执恢复，完成步骤不能只凭内存标记跳过。能力需要补充业务输入时，Run 以 `awaiting_input` 挂起，原生问题及真实自由文本答案进入 Session 日志；Goal 自动恢复不处理这一原因。

## Alternatives considered

**每个能力步骤分别启动 Run。** 步骤之间的取消和项目 revision 会形成多个恢复边界，前一步的结果可能在后一步失败时已成为正式成果，无法作为一个任务协调发布。

**发布整个候选目录。** 工作树复制了任务开始时的完整基线，目录替换会覆盖无关章节及其他已有文件；精确文件清单与同批凭据将发布限制在实际变更范围。

**修改原 Work 请求以保存计划调整。** 请求 SHA 是恢复身份；修改它会使旧 Run 的授权和输入摘要失效。后续消息授权保存在检查点的补丁记录中。

## Consequences

一条用户任务在失败、停止和 Host 重启后仍由原 Work 身份恢复，已完成步骤和正式结果可独立校验，公开通知按 Work ID 去重。代价是每个适配器都须列出精确写入文件并提供业务校验；候选步骤失败留下的文件不能绕过结果回执进入正式项目。`BidTaskState` 仍是唯一项目状态，步骤记录不成为第二套总控状态机。

本决定扩展[Run 生命周期](2026-09-13-bid-workflow-run-lifecycle.md)的 Work 分发，并沿用[公共能力契约](2026-09-24-bid-capability-contract.md)的业务输入与范围校验。两份记录的 Run 权限、默认路线和只读项目查询规则继续有效。
