# Agent Note: 标书内部追踪身份与客户正文分离

Status: implemented

## Problem

Requirement、Scoring、Compliance、Response Point、Section 和 Acceptance Criterion 的稳定 ID 便于跨阶段追踪覆盖关系，却对采购方没有解释价值。模型把这些身份写入标题、总述或需求对应表时，内部工作制品会泄漏到正式标书；同时，按覆盖清单组织正文容易把纯资格和行政要求扩写成要求解读页，并让技术章节采用采购方审查口吻而非投标人直接作答。

## Decision

内部 ID 继续保存在分析制品、映射、审核报告和工作台数据中，生成和审核阶段的客户正文只接收自然语言、招标文件简要原文或采购方自己的条款编号。共享检查器从当前项目的 Requirements、Scoring、Compliance、Response Points、Outline 和 Writing Plan 收集真实身份，在 S3 目录校验、S4 父节点总述提交、S5 章节候选及最终 Validator 中拒绝这些身份独立出现。导出阶段的再次检查由[按已保存内容导出](2026-09-12-word-export-saved-content.md)替代，未审核正文也可导出。某个同名编号在招标原文中独立出现时，将其视为采购方编号并允许保留。

S3 目录任务和 Blueprint Quality Review 只把需要展开的技术方案、实施措施与交付成果组织成章节。纯投标资格、企业资质证书和行政递交 Compliance 留在 `global_compliance_ids`，不为覆盖关系创建正文页；混合事项只保留可直接作答的技术部分。

S4 父节点总述和 S5 正文以我方或本方案的工作方法、职责、流程、控制措施、交付成果和可核验承诺为主体。采购要求只在理解回应所必需时作为一句背景。企业事实、资质、业绩、人员和既有能力缺少本地 Evidence 时只进入 `unresolved_topics` 或全局合规审核，不在客户正文中复述要求、生成无依据承诺或写占位内容。需求对应表仍可存在，但不得把内部 ID 当作客户可读索引。

Chapter Reviewer 的 `quality_checks` 增加 `bidder_response_voice`；主要采用采购要求复述、资格解释、需求分析或审查报告口吻的候选必须回到同一 Writer 修订。章节审核格式版本提升为 6，首次正式发布前不读取版本 5。

## Related

S3 的目录生成与质量复核仍由[技术标写作蓝图](../feature/2026-08-30-bid-outline-generation-agent-stage.md)定义；S5 的章节并发、资料权限、补搜和持久化仍由[已确认目录的章节写作与按需研究](../feature/2026-08-30-chapter-writing.md)定义，动态验收协议由[S5 通用任务契约与动态验收](../architecture/2026-09-10-s5-generic-task-contract-acceptance.md)定义。本记录只拥有两阶段共用的客户可见正文边界。

## Alternatives considered

**只修改 Writer 提示。** 不采用；提示不能阻止目录总述、人工改写或旧制品把内部身份带到预览和导出，也不能为 Reviewer 提供明确的修订判据。

**按 `REQ-*` 等固定前缀扫描全部文本。** 不采用；项目身份来自正式制品且具体格式可能变化，固定正则会漏掉其他有效身份，也会错误拒绝不是本项目追踪记录的业务编号。

**禁止所有形似内部 ID 的编号。** 不采用；招标文件可能真实使用相同编号，客户可见文本需要保留采购方自己的条款索引。

**为缺少证明材料的资格事项生成说明页。** 不采用；要求解读和占位承诺既不增加有效响应，也会掩盖必须由投标人补齐的真实材料缺口。

## Consequences

目录和章节写作需要读取当前项目的身份制品，章节审核报告格式发生一次不兼容升级；通过生成与审核校验的正文不暴露内部追踪语言，纯行政合规不挤占技术正文，技术章节保持投标人直接作答。招标原文编号例外以项目全部招标原文为边界：同一身份一旦确实属于采购方编号，正文各处均可使用，语义是否引用得当仍由模型审核而非 Host 猜测。

## Testing

定向单元和无密钥 Loader 回放覆盖目录、父级总述、章节候选和 Reviewer 修订，并同时覆盖自然语言和采购方原有编号。真实模型最小场景包含纯资格 Compliance 与技术需求，用于检查目录取舍、投标人立场和最终客户可见文本。
