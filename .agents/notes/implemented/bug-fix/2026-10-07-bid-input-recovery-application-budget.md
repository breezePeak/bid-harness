# Agent Note: 原生输入恢复只为已开始的应用计数

Status: implemented

## Problem

原生问题可能等待用户数小时，Host 卸载会撤回当前提问。等待、答案落盘和恢复动作具有不同的完成时点；提问前预占执行次数会使预算为一的任务在尚未执行时阻断。恢复 Run 已接纳而输入日志尚未结算时，项目可能已经离开挂起状态，仅从当前阶段寻找问题不能补齐原应用记录。

## Decision

输入日志将准备失败与执行次数分开持久保存。`attempts` 在调用恢复动作前保存；普通等待、答案保存和未开始的取消不计执行。程序为每次应用生成与稳定问题身份、执行次数绑定的 SHA-256 标识。保存预占期间发生取消时只撤回该次尚未调用的动作；调用之后的取消保留次数，不推测副作用未发生。

答案保存后重启复用原答案。恢复通过原 Work、请求摘要、Run 和项目 revision 守卫，接纳身份保存实际 Run 和 epoch，再结算 applied。Host 启动从持久 `bid.run.started`、`resumeOf` 和原问题身份对账已经接纳的输入；对账只写结算，不执行、不重开旧问题，不越过后续用户停止。原预算只可缩小，真实失败跨重启累计。

本决定补充[恢复必须执行并结算](2026-10-06-bid-recovery-settlement.md)的原生输入应用计数与重启对账；该记录仍拥有 Main 恢复调度、原 Work 授权、模型修复预算和其他执行器故障分类，因此保留活跃。

## Alternatives considered

**所有 abort 都退还次数。** 取消可能发生在恢复 Run 已接纳之后；统一退款会抹去真实执行，允许跨重启扩大预算。

**只从当前挂起阶段寻找旧问题。** 接纳后的项目可能是运行中、待确认或已经完成，旧日志仍需按权威事件补结算。

## Consequences

准备失败使用独立有限次数，保存与应用故障都有明确诊断。磁盘应用标识必须匹配执行次数，accepted 状态必须包含实际 Run 身份。进程在应用记录落盘之后、调用之前直接崩溃时，持久 applying 状态不能证明没有执行，保守保留该次执行次数；可观察的 Host 取消则能在收口期间撤销未调用预占。

## Testing

真实 Host、Agent 与 JSONL 持久化使用临时文件覆盖预算一和默认三的提问卸载、答案落盘中断、接纳后未结算重启；已接纳只补 applied。实际 `stopRun`、持续暂态失败、权限与额度故障、提问失败独立计数和预占期间取消分别验证停止、阻断与预算。无密钥 Loader 回放使用真实导入与 DOCX 解析失败，跨三次启动验证提问取消、答案复用、实际接纳和重启结算。可控 provider 验证协议和生命周期，不代表真实模型语义效果。
