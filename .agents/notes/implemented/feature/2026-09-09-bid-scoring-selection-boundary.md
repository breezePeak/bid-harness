# Agent Note: S2 评分事实与人工响应选择分离

Status: implemented

## Problem

S2 的完整评分抽取同时承担事实保存和后续响应范围选择。若用户通过删除评分项表达“不纳入后续响应”，原始评分事实会永久丢失；若把是否必答当作筛选开关，又会混淆招标语义与用户工作决定。刷新审核页、切换 Session 或重新确认时，未持久化的筛选也无法可靠恢复。

## Decision

S2 Host 发布时把完整评分事实写入 `analysis/scoring-origin.json`，并创建 `analysis/tender-analysis-selection.json`，默认按原始顺序选中全部评分 ID。审核页始终展示原始评分集合，将 `must_answer` 的规范化编辑与“是否纳入后续响应”分别呈现；每次选择变更立即由 Host 校验 ID 并原子持久化，不能修改评分事实。

用户确认 S2 时，Host 以原始评分、当前选择和受控规范化编辑生成 `analysis/scoring.json`。正式文件只保留选中项，保持稳定 ID 和原始顺序；未筛选时与原始评分集合一致。确认通过后，Host 将 S2 的模型可见上下文替换为仅声明正式评分 ID 的交接消息，避免同一 Main Agent 从旧原始评分中恢复已排除项。S3、S4、S5 只读取 `scoring.json`，不判断选择记录，也不回退读取原始评分。S2 Validator 继续验证完整的 `scoring-origin.json`，而正式 `scoring.json` 由严格 Schema 解析和筛选投影产生。

重新执行或重置 S2 时清除旧原始评分、选择、正式评分和全部下游 Artifact；再次发布重新建立默认全选。确认失败不保留候选 `scoring.json`，因此下游不会读取未经确认或与当前选择不一致的评分集合。

## Alternatives considered

**直接删除未选评分项。** 不采用，因为这会把用户工作范围选择写回招标事实，后续无法审计模型抽取是否完整，也无法恢复被排除项。

**复用 `must_answer` 表示是否纳入响应。** 不采用，因为 `must_answer` 描述招标要求是否必须响应，人工筛选描述当前项目是否处理该评分项；两者可能独立变化。

**只在浏览器状态中保存选择。** 不采用，因为刷新、断线和换 Session 会丢失决定，最终确认也无法证明使用的是用户最后一次选择。

**让 S3-S5 同时读取原始评分和选择记录。** 不采用，因为每个下游阶段都要重复实现选择、缺失与顺序规则，并形成两条可能分歧的数据路径。正式 `scoring.json` 是唯一已确认边界。

**保留 S2 的完整模型上下文直到 S3 完成。** 不采用，因为同一 Main Agent 可以将已排除的原始评分重新写入 S3 候选，即使 S3 已读取正式文件；S2 确认时替换模型可见上下文，日志仍完整保留用于审计。

## Consequences

S2 增加一个完整评分 Artifact 和一个轻量选择 Artifact；用户能在不破坏原始抽取的情况下反复筛选，选择跨刷新持久化。S2 确认后聊天界面不再展示该阶段的模型上下文，但 Session 日志保留完整审计记录。下游协议保持单一路径，现有基于 `scoring.json` 的目录、证据和写作逻辑无需理解人工选择。

旧项目若只有 `analysis/scoring.json`，不会获得兼容回退，需从 S2 重新生成。全部评分均被排除时，正式 `scoring.json` 合法包含空数组；这表示用户明确选择不让任何评分项进入后续响应，不改变 Requirements 或 Compliance 的处理。
