# 全书读标、研究与写作规则

本文供 WorkBuddy 执行完整技术标任务时按需查阅，覆盖商务、资格和报价相关资料的登记与核对。记录格式与可执行工具以技能入口为准；本文提供业务判断规则，文字要求本身不构成程序强制校验。

## 确定任务与资料

从用户原话和已有资料确定项目、标包、投标主体、交付范围、截止时间、指定格式及允许使用的企业材料。用户要求完整技术标时，处理全书及其响应关系；用户只授权审核、局部改稿或目录调整时，按该范围执行。已有回答和明确授权持续有效，不因换阶段重复询问。

按资料用途区分招标正文、公告及补遗、答疑澄清、企业证明、产品或技术资料、历史标书、用户草稿、格式模板和公开研究资料。同一文件可有多个用途，但引用时说明此次使用的性质。文件名不能证明其版本、项目归属或权威性。

核对目录、正文、附件、表格和补遗是否可读。记录文件名、版本或日期、用途、读取状态和真实定位；定位可以是原文件页码、标题、表格、工作表或单元格。提取文本的行号不能冒充原 PDF 页码。扫描件需要当前环境可用的 OCR 或视觉阅读能力；未能辨认的关键表格、盖章处或技术参数保持待核，不凭上下文补写。

先整理会影响全书的必要输入缺口，再集中询问。缺少企业证书可以继续方案设计与公开研究；缺少招标正文、标包归属或决定整体技术路线的必要条件时，只暂停依赖该输入的工作。对会改变价格、交期、资源投入或责任承诺的选项，不替用户作未经授权的决定。

## 读标与响应矩阵

先阅读采购范围、评分办法、实质性要求、交付验收、合同条款及文件组成要求，再沿其引用阅读附件和表格。搜索用于定位，完整语境用于判断；只看到命中摘要时不能宣称已读完相应条款。

将每条实质要求拆成可分别响应和复核的事项，同时保留原文定位。数字、单位、比较符号、否定词、时限、条件和例外不得在概括中改变。一个表格单元格可能对应多个事项，同一事项也可能横跨表头、脚注和相邻条款。

每个事项至少说明以下内容：原文与位置、规范化要求、事项类别、是否强制、适用对象、对应分值或评分规则、拟响应位置、所需依据、当前缺口。记录之间的身份和引用由可用程序生成、解析和绑定；模型只选择已有对象并填写语义内容，不手工编造标识。

| 类别 | 处理方式 | 不应混入的内容 |
|---|---|---|
| 技术需求 | 分配到具体方案、措施、设备或交付章节，保留参数和验收条件 | 用概述段落替代必须逐项应答的技术指标 |
| 技术评分 | 拆成可观察的评分响应点，并规划正文、图表或成果证明 | 只复制评分标题，漏掉标题下的情境、完整性和可行性条件 |
| 商务与合同 | 建立条款、响应材料、承诺和待决事项矩阵；需要时形成相应分册 | 未授权接受违约责任、付款条件、交期或合同偏离 |
| 资格与企业证明 | 登记所需文件、适用主体、有效期、签章要求和现有证明位置 | 以公开介绍、拟议方案或其他企业材料替代正式证明 |
| 报价与价格评分 | 提取计价口径、税率要求、数量、汇总关系和报价表结构；仅使用获授权的实际数值 | 推测成本、利润、折扣、税率、优惠承诺或最终报价 |
| 递交与形式要求 | 登记份数、命名、格式、签章、文件限制、渠道和时间，留给交付核对 | 把文件已经生成等同于已经签署、上传或递交 |

评分点以采购方实际评价对象拆分。例如“实施方案科学、完整，包含进度、人员及风险措施”需要分别规划实施方法、里程碑、岗位投入和风险处置，还要核对其相互一致；不能凭经验额外声称某个维度占几分。原文没有明确分值时保留未知。

发现正文、附件或补遗冲突时，记录相互矛盾的原文和位置，按采购文件明确规定的解释顺序核对。没有可确定的优先关系时，请用户或项目负责人判断，不把“发布时间较晚”直接当作所有场景的效力结论。

技术偏离表按要求逐项填写，实际响应、偏离判断和证明位置保持对应。不能因为目录覆盖了某条要求就自动填写“完全满足”；没有数据或产品依据时列为待核。商务偏离和技术偏离分别处理。

## 目录与章节职责

优先遵守采购方指定目录、编号、表格和分册要求，其次采用用户已确认的框架，再按业务任务补足结构。已获授权的目录可直接推进；只有存在互斥方案、改变交付范围或用户要求确认时才停下来请其选择。

为每个实际写作章节明确：本章解决什么问题、必须回答什么、服务哪些需求和评分点、需要什么依据、产生什么成果、与其他章节如何衔接。父章介绍整体方案，叶章展开可执行内容；不要求每个父章重复其所有子章的评分响应。

用响应矩阵反查目录是否遗漏强制要求、评分情境和必要证明。一个要求可以由多章共同响应，但应标明主响应和补充位置，避免责任分散。纯资格证书、行政递交条款和报价材料应进入适合的分册或资料矩阵，不为了“覆盖”而变成技术方案解读章节。

目录深度取决于采购任务和可展开内容。已有材料不足以支撑独立小节时，合并表达或记录研究缺口，不按固定层数扩章。不要使用“需求分析与理解”替代本应直接交付的实施方法、质量措施和成果。

共用背景、相似资料或工作时序不必构成写作依赖。只有某章必须使用另一章已确定的接口、指标、成果结构或职责决定时，才等待该成果；其他章节可以先写。记录这些真实关系，供后续变更判断使用。

## 按问题研究资料

研究从章节的具体缺口出发，例如“适用于此场景的验收方法”“标准现行版本”“接口兼容限制”“风险如何检测和处置”。使用 WorkBuddy 当前实际可用的搜索、浏览、文档阅读及已连接资料能力，不假定存在特定工具名称，也不另建搜索服务。

先利用用户授权的企业和项目材料，再查权威公开来源。标准和政策优先核对发布机构，产品参数优先核对厂商正式文档，技术方法优先采用适用的规范、技术文档或原始研究。权威性、时效性和场景适用性分别判断；较新的文章不当然适用于旧版设备或指定标准版本。

查询语句可以结合行业、业务对象、场景约束、技术问题及待核版本，但不得将机密资料、未公开报价、人员证件或客户敏感信息直接发给公共搜索。需要外发敏感内容或访问未获授权资料时，先确认权限；普通公开技术查询按已授权任务推进。

搜索结果摘要只作为候选线索。实际采用前打开来源并阅读相关正文、上下文和必要附件；表格数值同时核对表头、单位和脚注。保存原文摘录或允许保存的快照、来源名称、完整 URL 或本地位置、发布日期或版本、访问日期、支持的具体观点及适用限制。

| 研究结果 | 可采取的动作 | 不得声称 |
|---|---|---|
| 已读正文，内容与场景相符 | 作为相应事实或技术方法的候选依据，并记录范围 | 整个来源支持未读部分中的全部结论 |
| 只有搜索摘要、缓存标题或他人转述 | 继续找原文或可替代原始来源，保留未核实标记 | 已核验标准号、参数、版本或具体结论 |
| 网页失败、权限不足、下载失效 | 记录具体障碍，使用合法可访问的替代来源；继续其他研究 | 没搜到就等于不存在，或编写引用填补空白 |
| 多个来源冲突 | 比较对象、版本、日期和使用条件，记录差异 | 任意挑选最有利数值而不解释差异 |
| 企业能力或资格材料缺失 | 形成需要用户提供的具体材料清单，继续不依赖它的方案部分 | 公共资料或同类企业信息证明投标人的现实能力 |

研究以任务就绪为结束条件：关键回应有适用依据，拟议方案有清楚的设计条件，仍缺的事实能够明确列出。不要固定搜索多少篇，不因资料条数少就无限补搜，也不因找到一篇材料就跳过关键事实核对。

## 章节答题卡：事实、方案与缺口

写正文前，逐项列出本章回应、依据、适用范围和待补输入。一个要求可以同时有可写的方案部分和待补的企业事实，不必把整章一并阻塞。

| 分类 | 成文方式 | 需要保留的记录 |
|---|---|---|
| 有依据的事实（supported） | 只表达实际材料支持的对象、条件和范围 | 已读原文、真实定位及支持关系 |
| 本次拟议方案（proposal） | 以“本方案拟采用”等方式说明方法、角色、步骤、检查点和成果 | 设计目标、依据的采购条件、假设和适用限制 |
| 真实缺口（gap） | 暂不写成已具备事实或确定承诺，在内部问题清单登记 | 缺少什么、影响哪项响应、需要谁提供哪份资料 |

章节职责、模型总结和另一个章节的复述不能证明现实事实。网页资料和历史标书可支持适用的技术思路，不能证明本企业资质、业绩、人员履历、库存设备或特定产品已达到某项指标。企业官网宣传可作为检索线索；要求正式证书、合同或检测报告的事项仍须使用相应证明。

允许提出满足采购要求的实施方法、分工、表单字段、检查机制和质量措施，不要求采购文件逐字规定每一项设计。涉及已有人数、既有能力、硬性性能、工期或财务承诺时，必须核对真实输入及用户授权。

例如，没有企业人员材料时，不写“我司拥有 20 名持证工程师”；可以在确有授权的拟议人员配置中说明岗位职责和配置原则，将实际名单及证书登记为待补。没有确定性能依据时，不写“保证在 1 秒内完成”；应核对招标指标和产品数据，或先说明测试方法，将确定数值留待确认。

## 逐章写作

使用已经就绪的章节答题卡、确认目录和适用材料，直接编写可给采购方阅读的正文。每个核心措施应说明适用对象、执行角色、动作、时点或触发条件、检查方法及交付成果；只在对方案有帮助时展开，不机械堆砌字段。

避免主要复述“采购方要求”“应当满足”，改为本项目拟执行的措施。弱表达如“加强管理、确保质量”应具体到谁检查什么、发现问题如何处理、形成何种记录。不要以大量行业背景、重复承诺、泛化套话或任意章字数填充篇幅。

| 常见问题 | 应采用的表达方向 |
|---|---|
| “按照要求做好项目质量管理。” | 写明检查对象、负责岗位、检查节点、缺陷登记和整改关闭方式。 |
| “本系统符合所有国家标准。” | 列明已核验且适用的标准、版本与适用范围；未核验项目保留待核。 |
| “参考项目已在三十个城市成功上线。” | 只有当前投标人确有适用证明才能作为业绩；否则只借鉴技术方法，不迁入案例事实。 |
| “此处补充人员证书。” | 将证书缺口放入内部资料清单；正文与交付状态明确区分待补草稿和可提交版本。 |

采用历史标书时，逐项清理旧项目名称、采购人、地点、日期、数量、金额、人员、工期、环境、指标和客户事实。用户要求逐字保留的原文按[变更与交付规则](revision-and-delivery.md)处理；保留文字不等于该文字已经适用于本项目。

图表用于说明过程、职责、接口、进度、参数或成果。模型提出语义内容，当前可用的程序或文档工具负责布局、编号和生成；检查引用与实际图表是否一致。原材料缺少数据时，不用看似精确的图表补造数据。

商务和资格资料按矩阵归集并检查实际存在的证明；报价仅依据用户授权的数值和公式生成。计算由可用表格或程序工具执行，保留单位、含税口径、舍入规则和汇总关系，金额变化交由有权限的人确认。

## 审查与定向修订

写作后先核对文件可读、结构完整、引用可定位和响应矩阵覆盖，再进行内容审查。程序检查只能证明其实际执行的机械条件；语义充分性、事实支持和方案可行性仍需逐项阅读判断。

当前环境支持独立任务或独立审查上下文时，将冻结的正文、适用要求、证据原文和用户验收条件交给另一个审查任务。无法隔离时，用同一会话重新阅读成稿并明确记录为自审。更换角色名称或写一句“你是审查员”不能证明独立审查，更不能证明使用了独立模型。

审查至少覆盖以下方面：强制事项是否回应、评分情境是否展开、声明是否有适用依据、内容是否属于本章、是否采用投标人作答口吻、旧项目事实是否残留、跨章术语和参数是否一致、商务资格材料是否齐备、用户要求是否在实际成稿中体现。

每条问题记录实际位置、问题原文、违反的要求或缺失依据、影响及建议动作。把可由修改正文解决的问题、需要企业补料的问题、需要用户决策的冲突分开。对真实外部缺口不重复要求写作者改写，也不以“润色”制造事实。

优先修订受影响的最小范围，保留无关正确内容；涉及跨章决定时同步检查真实关联章节。修订后重新检查修改项及其影响，不自动把旧审查结论继承到已变化的正文。全书交付前仍需一次跨章核对，其状态与交付限制见[变更与交付规则](revision-and-delivery.md)。
