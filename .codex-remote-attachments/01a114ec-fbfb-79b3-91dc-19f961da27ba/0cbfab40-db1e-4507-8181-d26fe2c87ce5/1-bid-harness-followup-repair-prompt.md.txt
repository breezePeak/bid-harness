# bid-harness 后续五项问题修复提示词

请直接在当前仓库实现下面五项修复，并补充回归测试。这是上一轮恢复机制修复后的增量任务，不要重新推翻已完成的恢复驱动、输入日志、错误分类和重试预算设计。

## 基线与执行约束

- 审查基线：[8c5bb4591620e04abf28d09ae6e17a0cb83d218b](https://github.com/breezePeak/bid-harness/commit/8c5bb4591620e04abf28d09ae6e17a0cb83d218b)。下面行号仅用于定位，先读取当前 HEAD、差异、适用的 AGENTS.md 和项目说明，确认问题在当前分支仍成立；已经修复的项验证即可，不要回退新代码。
- 先找到真实调用链和复现场景，再做最小完整修复。保留用户未提交修改；不自动提交、推送、合并或部署，不自动调用付费真实模型/API。
- 大模型负责语义判断、研究策略和修正建议；程序负责 ID、引用身份、产物绑定、状态转换、预算、幂等和调度。不得让模型抄写内部 ID 来弥补程序缺陷。
- 保留 user_stop、权限/额度、输入版本和范围守卫。恢复必须有界，不能靠无限重试、放宽校验、伪造参考资料或改成“成功”解决。保留同一 Work 的任务关系、有效产物和恢复预算；允许既有协议创建新的物理 Run，不强求 Run ID 不变。
- 以下静态发现不等于真实模型端到端复现。分别记录“已复现缺陷”“条件性风险”“当前已修复”，以实际证据为准。

## 1. 输入恢复：等待回答不应消耗执行恢复预算（P1）

定位：`packages/bid/bid/src/index.ts` 2346–2423 的 `driveInputRecovery`，2504–2545 的提问回调，3479–3493 的 Host disposal；`bid-input-recovery.ts` 42–68 的 attempts 持久化。

当前风险：驱动在提问/应用答案回调之前增加 attempts。等待回答时 Host 关闭导致 abort，预算仍已消耗。预算为 1 时，一次这种中断即可阻断后续恢复；默认 3 时需多次中断，不能把一次中断必挂当成默认行为。

修复要求：
1. 明确区分等待回答、答案已保存、开始应用、应用已接纳、可重试失败、阻塞等状态。只有真正尝试应用恢复动作时才计入对应执行预算；提问失败如需预算，单独建模，不能混用。
2. 用户尚未回答的正常等待、Host disposal 或应用尚未开始的取消，不能被当成恢复动作失败。不能简单对所有 abort 退还次数，否则可能抹掉已发生的执行。
3. 答案、应用标识、接纳记录和计数需可持久恢复。答案已保存后重启不重复提问；resume 已接纳但本地尚未结算时先对账，不能重复启动。重启不能重置真实失败次数，也不能绕过用户停止。

验收：预算 1/默认预算分别覆盖“提问中重启”“答案落盘后、resume 前重启”“resume 已接纳、结算前重启”；未执行不能耗尽，已接纳不能重复执行。真正可重试失败持续累计并最终明确阻塞；权限/额度等非暂态错误不进入自动重试。

## 2. Web 抓取：错误元数据必须穿过真实工具池（P1）

定位：`evidence-mapping-executor.ts` 4339–4345 的父级 raw fetch、4533–4547 的观察器；检查真实 pool 118–122 的 `ToolArgsError(message)` 包装及错误分类器 223–248。通过符号/导入定位实际文件，核对 code、statusCode、retryAfter 的完整传递链。`fixtures/evidence-mapping-loop` 173–190 的现有 fixture 主要覆盖 search，不能代表 fetch 链已通过。

修复要求：
1. 将 search 与 fetch 的暂态失败统一归一化，保留原始 cause、机器可判定 code/statusCode、合法 Retry-After 信息，覆盖真实池包装及父级调用路径。不要仅修改最终分类器或只匹配英文报错文本。
2. 检查父级抓取不进入现有子级观察器的分支，确保该路径也进入相同的分类、退避和预算管理；避免观察器与调用方双计数、双重试。
3. 保留现有内部取消时的原始 Web 原因，以及同一 Work 跨 Run/重启的预算。区分网络暂态 429/5xx/timeout 与认证、明确额度耗尽、用户取消、无结果、页面无可用内容；不能把所有 429 都无条件重试。

验收：走生产 Tool/Pool 包装，用 fake provider 注入 search/fetch 的 429+Retry-After、503、timeout、401、明确 quota 错误及成功空内容。断言原始字段到达最终分类/日志，暂态按预算退避恢复，非暂态正确阻塞；覆盖父级 raw fetch 和子级工具路径、重启不刷新预算。

## 3. 独立能力完成后，同一 Work 的后续修正入口应一致（P1）

定位：`index.ts` 5715–5721 接受原阶段 ready/waiting_user/completed，5799–5803 恢复原状态；`bid-recovery.ts` 31–41 的 completed 判断；`index.ts` 3607–3612 中 `bid_plan_task` 对 failed/suspended 的 fallback。

当前风险：独立能力完成后阶段可能恢复为 ready 或 waiting_user，但后续修正入口只覆盖部分完成/失败状态，造成同一 Work 的继续路径不一致。另建 Work 可能仍可执行，不能把本问题描述为所有局部修改都不可用。

修复要求：
1. 用统一的 Work/能力执行记录判断能力是否已完成、是否允许继续修正，避免各入口用互不一致的阶段字符串推断。阶段状态和能力状态应各自准确，不能为打开入口把全部项目改成 completed。
2. 正常完成后追加修正、失败恢复、用户停止、等待真实输入分别处理。用户明确的新修正应绑定目标 Work、范围和最新有效产物；禁止错误复活停止任务、消费别的输入问题或重复执行已完成动作。
3. 核对能力产物提交、阶段状态同步、下一步调度的先后与幂等；局部目录变化后应准确使相关下游绑定/正文失效，保持无关章节不变。不要通过每次新建 Work 绕开原 Work 的预算和上下文。

验收：原阶段为 ready、waiting_user、completed 时，独立能力完成后分别追加同 Work 修正，检查入口接纳、产物版本、范围和后续推进；重复指令/事件不重复执行。另测 failed/suspended、停止、输入版本过期、无关 Work、真实缺资料边界，确认原有守卫有效。

## 4. 零参考资料：补齐可诊断的研究过程和真实充分性验收（P1）

定位：`evidence-mapping-executor.ts` 2922–2924 允许零 Web、809–815 的空数组、1534–1578 的保存、2949–2951 招标书/框架不作为 Evidence、2068–2110 的 sufficient 判断；沿产物继续检查参考资料列表展示。

零引用本身不必然是错误。本地资料可能足够，某些章节不需要外部证据；招标原文与参考 Evidence 又有不同身份。不要强迫每章联网，不设置凑数量门槛，不把空数组全部判失败，也不要把招标书换个标签伪装成参考资料。

修复要求：
1. 按研究范围记录实际证据需求及充分性理由。区分“不需要外部资料”“本地足够”“未发起研究”“已检索无相关结果”“抓取失败”“已读但未采用”“已保存未绑定”“绑定存在但展示过滤”等状态。
2. 程序记录真实事件：检索意图/查询、执行结果、候选来源、抓取/读取状态、采用或排除原因、保存和章节绑定结果；引用 ID、文件/分块定位由程序生成并校验。模型不得仅声称“已搜索”就被记为成功。
3. 对确实存在的证据缺口，触发有界的查询调整/替代来源/补充研究；仍不足则保留具体缺口和阻塞原因。只有确需用户提供的信息才询问用户，不能用笼统“资料不足”掩盖程序链路失败。
4. 将上述诊断持久化并连接到阶段执行和独立研究两条路径，前端能区分没有引用与没有执行。证明“搜索→抓取→读取→保存→绑定→展示”的每个交接点，不能只增加日志字段却不发布。

验收：覆盖本地足够不联网、真实无需引用、Web 命中并读到正文、搜索空、抓取失败、读后排除、保存成功绑定失败、绑定成功展示遗漏。确需证据但未研究不得无理由 sufficient；合理零引用可通过并解释。检查实际产物和 UI 数据契约，不能只断言工具调用次数。

## 5. DOCX 视觉缓存：最终页面变化必须使相关结论失效（P1）

定位：`docx-visual-review.ts` 306–324 的缓存键（块/模板/样式/几何）、390–396 的 passed 缓存跳过、420 的 outputHash 保存、445–447 的修正后整文档重渲染；`docx-visual-review.spec` 173–187 仅重查 A 的测试假设。

当前风险：周围正文、分页或后续修正会改变最终页面，即使图表块自身未变，旧 passed 也不一定有效。当前测试不能证明跨块排版变化已覆盖。

修复要求：
1. 缓存命中必须能证明被审查的视觉输入仍对应当前最终渲染。可采用相关页面/截图内容 hash、上下文依赖或更保守的整文档渲染版本失效；根据实际 renderer 选择可靠方案，不仅记录 outputHash 而不比较。
2. 后续修正重渲染后，使受到分页/布局影响的既往结论失效并复查。无法可靠判断影响范围时采用保守复查，不能假设改 A 永不影响 B。
3. 设定有界的修正→重渲染→复查闭环。最终交付须对应最后一次渲染和有效验收集合；超预算明确失败，不能沿用旧通过结果。保持无需变化时的安全缓存复用。

验收：仅修改图表前正文长度导致跨页；修改 A 推动 B 换页；后检查块修复影响先检查块；模板/样式/几何变化；真正相同视觉输入缓存命中。验证最终输出 hash 与验收关联，不用 fake“看过”冒充真实视觉模型验收。

先写能暴露原问题的回归测试，修复后执行受影响单测、真实 Host/Agent 生命周期集成测试、类型检查和项目要求的相关检查。网络/模型可用 fake provider，持久化用真实临时文件；必须经过实际工具池、事件订阅、状态机和重启恢复边界，避免 mock 掉本次故障节点。

最终逐项说明：当前 HEAD、是否复现、根因、修改文件、行为变化、验收命令及结果（通过/失败/未运行）、剩余限制。真实模型、真实招标书、真实 DOCX 渲染/视觉验收若未做，要明确标注；测试存在不等于测试通过，测试通过不等于真实模型效果已验收。附五项对应的回归证据和可复用验收步骤，不宣称“所有问题已解决”。
