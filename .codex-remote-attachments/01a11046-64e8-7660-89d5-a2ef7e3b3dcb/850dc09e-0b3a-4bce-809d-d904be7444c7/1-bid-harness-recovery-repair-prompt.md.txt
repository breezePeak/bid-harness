# bid-harness 挂起与恢复链路修复提示词

请在当前 bid-harness 仓库中完成以下 8 项问题的核验、最小修复与回归测试。目标是让已获授权的任务在可恢复故障后继续推进，真正缺少用户输入时才等待用户，并使每次恢复都有可核验的状态结算。直接开展工作，不要只给建议或要求用户逐条指挥。

## 先核验现场

- 阅读仓库 README、适用的 AGENTS.md、相关运行与测试说明；需要时读取仓库 `.agents/skills` 中相关技能。
- 记录当前仓库、分支、HEAD、工作区和暂存区差异。静态审查基准为 `b24f995ef6207ea2b072f02f89ea0588c1cf6fe5`，核对当前 checkout 与基准的相关差异。
- 下列发现都是静态代码审查线索，不代表已运行复现。逐项先追踪当前调用链，补最小失败测试或真实生命周期故障注入，再修改。当前版本已修复、触发条件不成立或判断有误的项目，保留验证证据并说明差异，不为凑齐 8 项硬改。
- 不切换或重置分支，不覆盖、撤销、格式化无关用户改动，不自动提交、推送、合并或部署。涉及冲突改动时先保留现场；仅真正无法安全继续时提出具体阻塞。
- 下文业务文件均位于 `packages/bid/bid/src/`，行号对应上述固定 SHA；通过符号与调用关系定位当前代码，不机械套用旧行号。

## 必须保持的设计边界

1. Main 负责语义判断与修复决策；程序负责生成 ID、绑定 Run/Work/检查点、执行、落盘、状态迁移、预算、幂等和结果校验。不要把运行时职责交给模型凭文字自觉完成。
2. 默认没有 active/armed Goal 也能恢复。Goal 可以复用恢复能力，但不得成为失败唤醒、续行或最终结算的必要条件。
3. 恢复保持原 Work、恢复链与有效检查点关联，仅重做失败的必要步骤。若现有恢复协议允许接纳新的执行 Run，按该协议记录身份迁移并保留有效产物；不得新建无关联任务、整章重写或清空状态来规避失败。
4. 保留正式正文、已验收候选、内容 hash、授权与范围校验、并发锁及用户停止/取消边界。恢复不能扩大已授权范围，也不能使未验收内容进入正式产物。
5. 优先在现有状态、事件和调度框架内最小修改。只有多个问题确实共享机制时才抽取小型共用逻辑，不另建一套编排架构，不顺手重构无关模块。
6. 禁止无限重试、吞错、放宽质量门禁、伪造成功、删除失败证据，以及仅增加提示词承诺。鉴权、不可恢复配额、权限及安全授权问题不得靠重试或降级绕过。

## 共用恢复与结算约定

先检查已有实现并复用；只补缺失能力，不强制采用以下字段名称或新增全部枚举。

- 区分外部输入不足、Main 可修复的内容/计划问题、可重试执行故障、不可自动恢复故障、用户停止/取消；保留结构化错误码、cause、发生阶段和取消来源。
- 对恢复记录持久化身份/版本、失败指纹、已选策略、尝试次数与预算、授权依据、执行结果及下一步。由程序生成和绑定身份；模型给出语义决策，程序校验后执行。
- 每轮必须结算为：已验证恢复并推进、已安排有界续行、明确等待具体外部输入，或终止并报告具体 blocker。仅向 Main 发消息、Main 回一段文字、仅写日志，都不算完成恢复。
- 明确单次操作重试和 Main 纠正轮的有限预算、退避与总上限；优先沿用仓库预算，缺失时选定合理有限默认值并测试。预算跨事件重复投递及进程重启保持，不靠重启清零。
- 对同一失败事件采用幂等去重；允许预算内有退避的瞬态重试。进入 Main 纠正后仍出现同一失败指纹时，必须选择有依据的新策略或结算阻塞。不得因通知已发而永久失活，也不得无限重放相同无效动作。
- 通过现有 Host 调度/事件机制确保工作被再次执行；每次到期唤醒或重启恢复都先校验授权、版本、锁及用户停止状态。禁止额外并发执行同一 Work。

**触发**：修订结果只有 `assignment_conflicts`，没有 `external_input_gaps`，也没有 `revision_issue_checks.needs_input`，但 attention 被统一转换为 `needs_input`，最终真正挂起。

**修改**：
- 在 executor、capability 适配与 Host 消费链路中保持原因类型，不根据 attention 总状态直接推导用户输入不足。
- 纯内部 assignment 冲突保留具体冲突及上下文，交给 Main 纠正分工/计划，并进入可执行的恢复路径。
- 只有真实外部输入缺口或明确的 `revision_issue_checks.needs_input` 才进入用户问答；混合情况保留两类原因，提问只涉及外部缺口。

**必须通过用例**：纯冲突不产生用户问题且实际触发 Main 修复；纯外部缺口准确等待；混合原因不丢冲突；普通写作与修订行为一致；门禁未通过前不发布候选正文。

## 2 Main 收到一次失败提醒后没有继续执行与结算

**定位**：`index.ts:2887–2928` 的失败 steer 去重，`index.ts:3100–3108` 的 idle 分支。Goal 相关对照：`packages/goal/goal-round-driver/src/index.ts:200–208,294–298`。[固定版本入口](https://github.com/breezePeak/bid-harness/blob/b24f995ef6207ea2b072f02f89ea0588c1cf6fe5/packages/bid/bid/src/index.ts#L2887-L2928)

**触发**：失败只向 Main steer 一次；Main 只回复文字、未执行修复，之后 idle 不处理 failed，且没有可继续驱动的 active/armed Goal。

**修改**：
- 增加或补齐程序可核验的恢复结算协议：记录 Main 决策是否落实、对应动作是否执行、原失败是否解除，而非仅记“已通知”。
- 在无 Goal 场景下，为未结算的失败安排有限纠正轮与后续调度；Main 无有效动作、调用失败或再次 idle 时仍有明确下一步。
- 对重复失败指纹，要求有依据地调整策略；策略或预算耗尽后，明确报告原始失败、尝试过的动作及 blocker，不伪装成等待用户输入。
- 恢复动作必须执行到可验证状态，遵守原 Work 的单执行者、恢复链与检查点约束；新执行 Run 的接纳须遵守现有恢复协议。

**必须通过用例**：无 Goal + Main 首轮仅文字回复仍能在后续轮推进；重复事件不产生并发或重复创建执行 Run；相同失败不无限循环；纠正成功后解除失败；预算耗尽明确结算；真实外部阻塞精准提问。

## 3 用户决策先标记收到 续行失败后无法再应用

**定位**：`index.ts:2324–2343` 先记录 `decision.received` 后 apply，`index.ts:2255–2257` 抑制重问，恢复锁/版本失败位于 `index.ts:5559–5581`，聊天恢复排除 `user_stop` 位于 `index.ts:3455–3458`。[固定版本入口](https://github.com/breezePeak/bid-harness/blob/b24f995ef6207ea2b072f02f89ea0588c1cf6fe5/packages/bid/bid/src/index.ts#L2324-L2343)

**触发**：用户已回答继续，答案已记录，但应用决策时锁冲突、版本冲突或执行异常；catch 只日志，后续又因已 received 而无法重试或重新进入有效恢复。

**修改**：
- 区分“收到答案”“应用中”“已应用”“应用失败”，可用现有字段表达等价语义。收到答案不等于续行成功；只在可核验落地后标记 applied。
- 持久化答案与应用状态，以程序绑定的稳定身份/版本保证幂等。重复回答、重复事件、进程重启及半途失败不能重复执行已生效动作。
- 用户已授权继续后，临时故障可在有限预算内重试同一授权动作；复用已保存答案，不要求用户再次回答相同问题。
- 锁/版本失败先重新读取并验证当前状态，不能盲目解锁、覆盖新版或错误消费检查点。身份不一致时明确阻塞。
- 用户 stop/cancel 不自动恢复；停止后用户明确要求继续时，按当前授权与检查点重新验证后应用，不能因为历史 `user_stop` 一律忽略新指令。

**必须通过用例**：收到继续后首次锁/写盘/执行失败再成功；重启后从持久答案恢复；动作已生效但确认落盘失败时不重复副作用；重复答案只生效一次；版本/身份冲突不错误恢复；停止期间零自动续行，新明确继续可安全恢复。

## 4 S4 内部退避取消吞掉原网络故障

**定位**：`evidence-mapping-executor.ts:4452–4457,4805–4807,4814–4826,4939–4951,5022`；真实取消语义见 `packages/core/agent-loop/src/agent.ts:143–149,313–329`。[固定版本入口](https://github.com/breezePeak/bid-harness/blob/b24f995ef6207ea2b072f02f89ea0588c1cf6fe5/packages/bid/bid/src/evidence-mapping-executor.ts#L4452-L4457)

**触发**：429、5xx 或 timeout 触发内部 `child.cancel`，真实 Agent 随后返回 aborted；上层先抛中止，未处理原始网络原因，后续又包装为不可重试普通错误，绕过内层网络恢复。Host 仍可能交 Main 恢复，不能把该线索描述为所有恢复都不可能。

**修改**：
- 在中止判断前保留并识别内部 backoff 的原始错误与取消来源，避免丢失结构化 retryable、状态码和 cause。
- 内部为退避而取消可按原网络故障进入有限重试；真实用户停止/取消保持终止。来源不明不得猜成可自动恢复；用户取消与内部退避竞态以用户停止意图为约束。
- 保留既有 429 降并发、退避和预算规则，避免内层与 Host 双重重试叠加失控；确保只保留一个有效执行者。

**必须通过用例**：通过真实 Agent 生命周期让取消产生 aborted，分别注入 429/503/timeout，验证原 cause 保留且恢复成功；耗尽预算后明确失败；真实用户取消无重试；取消竞态不越过用户意图。只让 mock 直接 resolve 成功不算覆盖。

## 5 保存写作要求后 计划模型临时失败不进入恢复

**定位**：`index.ts:2844–2854` 保留计划 `TIMEOUT`/`TRANSPORT` 等真实错误码，而 `bid-recovery.ts:247–252` 只接纳 `NOT_COMMITTED`/`DISPATCH_FAILED`。[错误产生处](https://github.com/breezePeak/bid-harness/blob/b24f995ef6207ea2b072f02f89ea0588c1cf6fe5/packages/bid/bid/src/index.ts#L2844-L2854) · [恢复判定处](https://github.com/breezePeak/bid-harness/blob/b24f995ef6207ea2b072f02f89ea0588c1cf6fe5/packages/bid/bid/src/bid-recovery.ts#L247-L252)

**触发**：用户写作要求已保存，后续计划模型临时 timeout/transport 失败；恢复判断漏掉这些类型，流程停住或重新问已回答的问题。

**修改**：
- 用结构化错误分类接入现有恢复机制；覆盖当前实际可重试类型，避免粗暴地将所有错误都设为 retryable 或仅扩充无语义的字符串白名单。
- 保留已保存要求、原始错误码与失败阶段，只重新执行失败的计划步骤；遵守有限预算、退避及幂等。
- 鉴权、不可自动解决的配额和真实缺业务输入分别明确阻断，不能改写成普通网络错误或反复询问写作要求。

**必须通过用例**：已保存要求后 timeout/transport 首次失败、后续成功；重启后要求仍可复用；不重复提交要求或重复启动写作；鉴权/配额与真缺输入精准分类；预算耗尽不悬空。

## 6 必需页数估算的执行异常被当成用户输入不足

**定位**：`chapter-writing-executor.ts:1815–1863` 的全 catch，`orchestrator.ts:443–456` 的 `completeRun` → `waiting_user`；底层 `page-estimate.ts:414–418`、`docx-format-store.ts:174–184`。[固定版本入口](https://github.com/breezePeak/bid-harness/blob/b24f995ef6207ea2b072f02f89ea0588c1cf6fe5/packages/bid/bid/src/chapter-writing-executor.ts#L1815-L1863)

**触发**：required `estimated_pages` 执行过程中，格式文件读取出现 EACCES/EIO、损坏等异常，被统一转成 attention，进而等待用户。默认 fast 估算并不依赖 LibreOffice，不得把该问题笼统归为缺少 LibreOffice。

**修改**：
- 区分实际页数未达标、真实业务输入不足、内部估算执行异常。页数未达标维持质量门禁并按授权交 Main 修复；只有缺业务输入才请求用户。
- 执行异常保留原 cause/错误码，进入 failed 与适合该原因的恢复路径；EACCES、损坏等不能一律自动重试，更不能关闭 required 校验或虚构页数。
- 在估算确实恢复并得到有效结果后再完成校验；失败期间保护已验收候选、正式正文及内容 hash。

**必须通过用例**：fast 路径正常运行无需 LibreOffice；注入 EACCES/EIO/损坏时分类与 cause 正确；可恢复故障修复后重新估算；实际页数不足仍被拦截；真正缺输入才等待；无结果不能宣称通过。

## 7 S4 全局审查上下文重复放大且溢出被当格式错误

**定位**：`evidence-mapping-executor.ts:3742–3797` 每个叶子重复展开 siblings，`3804–3827` 将 overflow 归入 stop_reason/格式重试，`3868–3873` 耗尽；`4758,5127` 的 48000 FinalCheck 分片未覆盖这段全局 review。[固定版本入口](https://github.com/breezePeak/bid-harness/blob/b24f995ef6207ea2b072f02f89ea0588c1cf6fe5/packages/bid/bid/src/evidence-mapping-executor.ts#L3742-L3797)

**触发**：大目录下同级信息被逐叶重复序列化，输入可能二次方增长；上下文超限后原样做格式重试，无法缩减上下文，最终失败。

**修改**：
- 消除逐叶重复的完整 siblings 展开，采用共享索引/引用及预算感知的上下文构造，记录可测试的输入规模与预算。
- 在请求前计算可用预算，计入指令、输入与输出余量；根据仓库支持的计量方式实现，不能混淆 48000 的字符/字节/token 单位。
- 必要时分层或分片审查，并做全局汇总。保留章节/证据的稳定覆盖映射及跨章关系检查，不能仅截断输入、只审前若干章、或删除 siblings 后声称覆盖完整。
- 对单个超大节点同样有界拆分或明确失败。保留结构化 context-overflow 错误，采取实际缩减/分片策略，不能对不变输入反复格式重试。

**必须通过用例**：小目录行为回归；大目录输入增长与每次请求均符合预算；末尾章节和跨章冲突 fixture 必须被审到；覆盖清单无漏项；单节点超大有界处理；真实 provider 形态的 overflow 走正确分类，不靠原样重试过关。

## 8 用户输入桥接失败后静默停留 awaiting

**定位**：`index.ts:2269–2307` 的 `ensureCapabilityInput` catch。[固定版本入口](https://github.com/breezePeak/bid-harness/blob/b24f995ef6207ea2b072f02f89ea0588c1cf6fe5/packages/bid/bid/src/index.ts#L2269-L2307)

**触发**：检查点读取、问题创建、答案保存或续行失败，异常只记日志；状态仍显示 awaiting，却没有有效问题、可消费答案或后续执行。

**修改**：
- 分阶段记录桥接状态与错误，让每个失败都有结算、有限重试及 Main 通知。只有有效外部问题确实待答时才保持等待用户语义。
- 对问题创建与答案保存使用现有稳定身份/幂等机制；重试不重复提问，不让尚未持久化的答案被当作可安全恢复的事实。
- 已持久化答案必须复用，续行失败转入应用/恢复流程，而非再次索要答案。
- 检查点缺失、Run/Work/问题身份冲突先验证当前状态和可恢复性，不能猜测绑定、伪造检查点或盲目续行；不可恢复时明确通知 Main 并报告具体 blocker。

**必须通过用例**：逐阶段注入失败后恢复；创建成功但回执失败不重复问题；保存答案成功后续行失败可复用答案；重启保持状态；缺失检查点/身份冲突不错误恢复；不能留下“awaiting 但无有效待答问题”的静默状态。

## 统一验证与完成门槛

按依赖组织小步修改，先跑对应失败测试，再跑修复后测试和相关回归。实现顺序自行决定，不要求用户逐项批准技术细节。

- **单元层**：覆盖错误分类、状态迁移、决策应用、幂等、指纹、预算及上下文构造；包含正常、失败、重复和边界条件。
- **Host/Agent 集成层**：可使用 fake provider 和可控时钟，但必须经过真实 Host 调度、真实 Agent 取消/终止事件、真实临时目录落盘及读取恢复。不得仅直接调用分类函数或 mock 最终结果冒充端到端验证。
- **故障注入层**：覆盖网络瞬断、限流、写盘失败、锁冲突、版本冲突、回答后崩溃、重复事件、Main 只文字回复、真实用户 cancel，以及无 Goal 场景。对关键“写成功但确认失败”窗口验证不重复副作用。
- **不变量层**：验证原 Work、恢复链与检查点关联保持，Run 身份迁移符合现有恢复协议且保留有效产物；同一 Work 无双执行者，正式正文与已验收候选/hash 未被越权修改，未通过门禁不完成，停止后无自动续行，预算不会因重启重置。
- **真实模型层**：已有允许使用的环境可做最小冒烟；不为完成本任务强制开付费 API、新增凭据或更改安全授权。没有运行就明确标为未运行，不能用 fake provider 推断真实模型已通过。
- **仓库检查**：执行 README/AGENTS 要求及受影响范围的测试、类型检查、lint、构建；最后一次相关修改后重新验证。针对性检查通过不等于全仓通过。
- 所有应执行的验收必须有实际命令、退出码和可追溯结果。测试未过、必要集成验收未跑或核心 blocker 未解决时，只报告部分完成与阻塞，不宣称修复完成。
